# Upstream Editor Improvements Port Design

## Summary

Port three merged Godot changes into Foundry using the upstream implementations as behavioral guidance:

- godotengine/godot#111375: documentation admonitions in editor help and `make_rst.py`.
- godotengine/godot#119588: ranged warning and error squiggles in the script editor.
- godotengine/godot#111086: use `Node`'s cached viewport when a `CanvasItem` enters the tree.

The port must fit Foundry's current architecture rather than reproduce Godot-specific integration. In particular, diagnostic ranges come from Foundry Script, not GDScript. The implementation will add regression coverage for behavior that the upstream pull requests left untested and will harden underline tracking around destructive edits.

## Goals

- Render `[note]`, `[warning]`, `[tip]`, and `[important]` blocks in editor help and documentation tooltips.
- Convert those tags to `.. classref_<type>::` directives in generated reStructuredText.
- Give Foundry Script warnings and errors precise source ranges and show configurable squiggly underlines for them.
- Keep diagnostic underlines aligned during the delay between a text edit and the next validation pass.
- Preserve the existing warning and error line backgrounds as independently configurable behavior.
- Restore the constant-time cached viewport lookup for `CanvasItem` without changing visibility semantics.
- Verify editor-facing behavior through the real editor when automation can exercise it reliably.

## Non-goals

- Converting existing bold `Note:` or `Warning:` prose throughout the class reference.
- Supporting nested admonitions in generated reStructuredText.
- Adding diagnostic hover tooltips or extending squiggles to non-script editors.
- Exposing TextEdit diagnostic decorations as a new public scripting API.
- Refactoring all editor decorations into a generalized decoration framework.

## Documentation Admonitions

### Editor rendering

The editor documentation parser will recognize four semantic tags. Each opening tag pushes a theme-derived color and bold label, then adds the corresponding editor icon. Closing tags use the existing tag stack, so editor help retains support for nested inline formatting and nested admonitions.

The modern and classic themes will define readable note, warning, important, and tip colors for both dark and light variants. The implementation will use Foundry's existing editor theme APIs and icon names. Packed-array copy notices generated by the editor will use `[note]` so the editor and generated documentation share the same semantic markup.

### reStructuredText generation

`doc/tools/make_rst.py` will treat the four names as reserved semantic tags and convert a complete block to a `classref_` directive with an indented body. Multiline and multi-paragraph bodies are supported. Surrounding prose is separated from the directive with blank lines so the generated output remains valid reStructuredText.

The generator will report unmatched closing tags, mismatched tags, unclosed blocks, and nested admonitions through its normal validation path. Nested admonitions remain unsupported in generated reStructuredText even though the editor renderer can display them.

## Ranged Foundry Script Diagnostics

### Coordinate contract

The `ScriptLanguage` boundary uses one-based line and column values. A range start is inclusive and its end is exclusive. The script editor converts the range to zero-based coordinates exactly once before passing it to `TextEdit`.

Foundry Script warnings will carry the complete source-node range already available when the warning is created. Parser errors will retain their existing start `line` and `column` fields for internal compatibility and gain an end line and column populated from the originating node or previous token. `FSLanguage::validate()` will translate both into the generic `ScriptLanguage` range structure.

Extension languages that only return the legacy `line` and `column` dictionary values will receive a one-character range beginning at that position. Invalid, missing, reversed, or out-of-document positions will be normalized by the editor before a decoration is added. A missing usable range falls back to the reported line and never reaches drawing code as a negative or reversed selection.

### Editor integration

Editor settings will gain warning and error underline colors derived from the active theme. Changing either setting updates existing decorations without waiting for another parse. Transparent underline and line-background colors are independent: users may enable either or both.

All editor consumers of `ScriptError` will move from a single line/column to the range start for navigation and messages. Dependent-script errors keep their current file-navigation behavior.

### TextEdit decorations

`TextEdit` will store internal colored underline ranges and draw them from shaped-text selections. This preserves bidirectional text and split visual selections. A clipped polyline produces the familiar squiggle, scales from font metrics, stops at the exact visual end of the selection, and skips empty or zero-width spans.

Decoration positions will be transformed by every text mutation that already transforms carets. The transformation rules are:

- Insertion before a range shifts both endpoints.
- Insertion at the start leaves inserted text outside the decoration by shifting both endpoints.
- Insertion inside a range moves the end so the original diagnosed text remains covered.
- Insertion at the end does not grow the decoration.
- Deletion before a range shifts both endpoints backward.
- Deletion overlapping an endpoint collapses that endpoint to the deletion start.
- Deletion covering a whole range collapses it to an empty range, which is not drawn.
- Line replacement, insertion, removal, and swapping preserve valid ranges and clamp them to current line lengths.

Test-only accessors guarded by `TESTS_ENABLED` will expose decoration count and values to C++ tests. They will not be bound through ClassDB or become supported runtime API.

## CanvasItem Cached Viewport

When a top-level `CanvasItem` without a `CanvasItem` or `CanvasLayer` parent enters the scene tree, it will use `get_viewport()` instead of walking ancestors to find a `Viewport`. `Node` populates its cached viewport before enter-tree notification, so this is equivalent for a `Window` and a `SubViewport` while avoiding repeated traversal.

Only a `Window` contributes visibility state and a `visibility_changed` connection. A `SubViewport` continues to make the item visible because it has no equivalent visibility state. Tests will cover both cases and ensure the optimization does not change behavior.

## Testing Strategy

Implementation follows red-green-refactor cycles:

1. Add Foundry Script tests that assert exact warning and parser-error start/end ranges through `FSLanguage::validate()`.
2. Add TextEdit tests for insertion, deletion, overlapping replacement, line insertion/removal, line replacement, line swapping, invalid ranges, color changes, and clearing.
3. Add a CanvasItem scene-tree test for Window visibility propagation and SubViewport behavior.
4. Add Python integration tests under `scripts/tests/` that execute `make_rst.py` against temporary XML and assert generated directives and validation failures.
5. Add an editor help test that feeds markup through a `TESTS_ENABLED` rendering wrapper and inspects the resulting RichTextLabel text for all four labels, nested inline markup, and surrounding prose.

Focused doctest suites and Python tests run during iteration. Before handoff, `python3 scripts/agent_build.py --test` performs the native strict build and full supported test run; relevant focused filters are rerun separately when they provide clearer diagnostics.

## Editor Verification

After the automated tests pass, launch the real Foundry editor with automation enabled. Open documentation containing all four callouts and a Foundry Script containing at least one warning and one parser error. Verify semantic UI state, editor logs, theme updates, and the rendered result. Capture proof screenshots and assemble a compact review gallery when the capture path is reliable.

## Compatibility and Failure Handling

- Existing documentation without semantic admonition tags renders unchanged.
- Existing extension language implementations remain source compatible with the generic validation API and receive fallback ranges.
- Diagnostics with unusable ranges retain line-level navigation and backgrounds without attempting an invalid squiggle.
- Empty shaped-text selections and clipped-offscreen selections do not submit invalid polylines.
- The CanvasItem change fails through the existing cached-viewport invariant rather than adding another tree walk.

## Expected File Areas

- Documentation generation and editor help: `doc/tools/make_rst.py`, `editor/doc/editor_help.cpp`, editor theme files, and documentation/tooling tests.
- Generic and Foundry Script diagnostics: `core/object/script_language*.h`, `modules/foundry_script/fs_parser.*`, `fs_warning.h`, `fs_editor.cpp`, and Foundry Script tests.
- Underline storage, transformation, and rendering: `scene/gui/text_edit.*`, `editor/script/script_text_editor.*`, editor settings/theme files, class reference XML, and TextEdit tests.
- Cached viewport lookup: `scene/main/canvas_item.cpp` and scene tests.
